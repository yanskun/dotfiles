# Diff Review → 実装 agent への FB

レビュー(自分の pane)と実装(別 pane の agent)を分離した並行開発フロー。
deliverable は「ユーザーへのレビュー報告」と「実装 agent への修正依頼」の 2 つ。

## 手順

### 1. diff の把握

- `git diff main...HEAD --stat` で全量を把握(working tree が dirty なら `git status` も)。
- 本文は生成物を除いて読む:
  `git diff main...HEAD -- ':!*.pb.go' ':!*_pb.ts' ':!*.bob.go' ':!*mock*'`
- 生成物は「配線漏れがないか」を stat レベルで確認するだけ(中身のレビューはしない)。

### 2. レビュー基準のロード

- 対象リポの CLAUDE.md / `.claude/rules/`(コメント方針・テスト規約・レイヤー規約)を基準にする。
  自分の一般論より repo の規約が優先。規約違反の指摘には該当ルールファイルを引用する。
- 過剰実装(投機的な抽象化・車輪の再発明・不要な依存)の観点は
  **ponytail:ponytail-review skill を併用**する。

### 3. 裏取りしてから指摘する

- 疑わしい点は diff の**外側**を読んで検証する: 値が流れる先(consumer)・validation ルールの
  実定義・既存コードの慣習・DB スキーマ。裏取りできないものは断定せず質問として出す。
- 指摘を分類して優先度をつける:
  **バグ(実害シナリオ付き) > 規約逸脱 > 過剰実装 > 設計論点(質問形) > コメント過不足**。

### 4. ユーザーへ報告

- severity 順に、実害シナリオと修正方針をセットで報告する。
- レビュー依頼の deliverable は評価。修正の実行やFB送信はユーザーの指示を待つ
  (「レビューして FB して」と最初から言われていれば送信まで進んでよい)。

### 5. 実装 agent への FB 送信

- 送信の仕組み(pane 特定・`$HERDR_PANE_ID` での自分除外・返信テンプレート・配達確認)は
  **herdr-agent-message skill に従う**。同一 worktree(cwd 一致)の pane が通常の送信先。
- FB 本文は 2 セクションに分離する:
  - **修正依頼(要対応)**: 裏取り済みの指摘のみ。絶対パス・修正方針・回帰テスト追加・
    修正後にテストを緑にする指示を含める。
  - **対応不要(user 判断待ち・触らないでください)**: 設計論点やユーザー確認が要る項目。
    実装 agent にスコープ判断をさせない。
- `--wait` のタイムアウトは送信失敗ではない。`herdr agent read <pane_id>` で相手が
  受信・着手したことを確認してからユーザーに報告する。

### 6. 回収

- 完了報告が来たら、修正差分を自分でも確認する(信頼するが検証する)。
- 来なければ `herdr agent read` で進捗を直接読む。無言で待ち続けない。
